# 프로젝트 에이전트 지침 — 공통

## 커밋 규칙

커밋을 생성하거나 수정(amend)하기 전에 반드시 이 규칙을 확인한다.
커밋만 요청받은 작업과 자동 생성되는 머지 메시지에도 적용한다.
현재 사용자의 명시적인 요청이 이 문서보다 우선한다.
커밋 규칙 자체는 커밋 실행 요청이 아니다. 사용자가 요청한 범위에서만 커밋한다.

### 형식

```text
<이모지>[라벨] 한국어 제목

* 설명 1
* 설명 2
```

- 이모지와 `[` 사이에는 공백을 넣지 않고, `]` 뒤에는 공백 하나를 넣는다.
- 제목은 한국어로 50자 미만으로 쓰고 마침표로 끝내지 않는다.
- `수정`, `변경`, `추가`만으로 끝나는 모호한 제목 대신 변경 대상과 결과를 쓴다.
- 한 커밋에는 한 가지 목적의 변경만 담고 라벨은 하나만 쓴다.
- 본문이 있으면 제목과 빈 줄 하나로 구분하고 `* ` 불릿을 쓴다.
- 변경 항목이 둘 이상이거나 임시 처리·하드코딩·후속 작업이 있으면 본문에 남긴다.
- `Fix`, `Design`, `Patch`는 제목에 현상이나 개선 대상 상태를 쓰고, 본문에 해결 방법을 반드시 쓴다.

### 라벨

| 이모지·라벨 | 적용 대상 | 제목·본문 기준 |
| --- | --- | --- |
| ✨[Feat] | 사용자가 사용하는 새 기능 | 제목에 기능 설명 |
| ⚙️[Core] | 공통 기반, 프레임워크, 내부 도구 | 제목에 기반 작업 설명 |
| 🐛[Fix] | 오류 또는 의도와 다른 동작 수정 | 제목에 현상, 본문에 해결 방법 |
| ♻️[Refactor] | 동작 변경 없는 코드 구조 개선 | 제목에 구조 개선 내용 |
| 🗺️[Design] | 사용 흐름, 구성, 동작 정책 조정 | 제목에 개선 대상 상태, 본문에 조정 방법 |
| 🩹[Patch] | 오타, 간격 등 작은 손질 | 제목에 개선 대상 상태, 본문에 변경 방법 |
| 🗃️[Update] | 데이터베이스 스키마, 마이그레이션, 데이터 변경 | 제목에 데이터 변경 내용 |
| 🎨[Asset] | 이미지, 아이콘, 폰트, 사운드 등 리소스 | 제목에 리소스 변경 내용 |
| 📝[Docs] | 문서, README, 주석 | 제목에 문서 변경 내용 |
| 🧹[Chore] | 패키지, 설정, CI, 파일 이동, 유지보수 | 제목에 관리 작업 내용 |
| 🔀[Merge] | 브랜치 병합 | 제목에 병합 대상과 목적 |
| 🔥[Del] | 기능 제거 | 제목에 제거 대상 |
| 🎉[Init] | 프로젝트 초기 커밋 | 제목에 초기 구성 내용 |
| 💚[Build] | 빌드 산출물 생성 | 제목에 버전 표기 |

### 라벨 구분

- `Feat` / `Core`: 사용자 기능이면 `Feat`, 이를 받치는 공통 기반이면 `Core`다.
- `Fix` / `Patch`: 크기가 작아도 잘못된 동작의 수정이면 `Fix`다. 정상 동작의 사소한 손질은 `Patch`다.
- `Design` / `Patch`: 사용 흐름·구성·정책을 의도적으로 조정하면 `Design`, 단순 오타·간격 손질이면 `Patch`다.
- `Refactor`: 동작이 달라지면 해당 목적에 맞는 `Feat`, `Fix` 등을 쓴다.
- `Asset`: 리소스 파일 자체의 변경에 쓴다. 기능 코드도 함께 바뀌면 변경의 주목적에 맞는 라벨을 쓴다.
- `Update` / `Chore`: 데이터베이스 변경은 `Update`, 의존성 패키지 업데이트는 `Chore`다.
- `Build` / `Chore`: 빌드 산출물 생성은 `Build`, 빌드 설정·CI 변경은 `Chore`다.

### 예시

```text
✨[Feat] 알림 수신 설정 추가

* 알림 유형별 수신 여부 저장
* 설정 화면에 유형별 토글 추가
```

```text
🐛[Fix] 저장 실패 시 입력 내용 소실

* 저장 성공 이후에만 입력 상태를 초기화
```

```text
🔀[Merge] 기능 브랜치를 개발 브랜치에 병합

* feature/notifications를 develop에 병합
```

자동 생성된 머지 메시지도 위 형식의 한국어 제목으로 정리한다.
브랜치명 등 구체적인 병합 정보는 본문에 남긴다.

### 커밋 전 체크리스트

- [ ] 이모지와 라벨이 표의 짝과 일치하는가?
- [ ] 한국어 제목이 50자 미만이며 끝에 마침표가 없는가?
- [ ] 한 가지 목적의 변경만 포함하고 제목이 구체적인가?
- [ ] `Fix`, `Design`, `Patch`는 제목에 현상, 본문에 해결 방법을 썼는가?
- [ ] 여러 변경 항목과 임시 처리·후속 작업을 본문에 남겼는가?
- [ ] 커밋 대상 diff를 확인하고 관련 없는 기존 변경과 비밀 정보를 제외했는가?
- [ ] 변경에 필요한 검증을 수행하고, 실패하거나 실행하지 못한 검증을 사용자에게 알렸는가?

## 파일과 작업 범위

- 소스와 문서는 기존 파일 형식을 존중하고 새 텍스트 파일은 UTF-8 BOM 없이 저장한다.
- 작업 전 저장소 상태를 확인하고 사용자의 기존 변경을 덮어쓰거나 되돌리지 않는다.
- 프로젝트에 기존 명령과 구조가 있으면 우선 사용한다.
- 완료 시 변경 내용, 검증 결과, 남은 제한을 간결하게 보고한다.
