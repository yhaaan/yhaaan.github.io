# 프로젝트 에이전트 지침 — 웹 개발

## 커밋 규칙

커밋을 생성하거나 수정(amend)하기 전에 반드시 이 규칙을 확인한다.
커밋만 요청받은 작업과 자동 생성되는 머지 메시지에도 적용한다.
현재 사용자의 명시적인 요청이 이 문서보다 우선한다.
커밋 규칙 자체는 커밋 실행 요청이 아니다. 사용자가 요청한 범위에서만 커밋한다.

### 형식

```text
<이모지>[라벨] 한국어 제목

* 설명 1
* 설명 2
```

- 이모지와 `[` 사이에는 공백을 넣지 않고, `]` 뒤에는 공백 하나를 넣는다.
- 제목은 한국어로 50자 미만으로 쓰고 마침표로 끝내지 않는다.
- 제목에는 변경 대상과 결과를 구체적으로 쓴다.
- 한 커밋에는 한 가지 목적의 변경만 담고 라벨은 하나만 쓴다.
- 본문이 있으면 제목과 빈 줄 하나로 구분하고 `* ` 불릿을 쓴다.
- 변경 항목이 둘 이상이거나 임시 처리·하드코딩·후속 작업이 있으면 본문에 남긴다.
- `Fix`, `Design`, `Patch`는 제목에 현상이나 개선 대상 상태를 쓰고, 본문에 해결 방법을 반드시 쓴다.

### 웹 개발 라벨

| 이모지·라벨 | 적용 대상 | 제목·본문 기준 |
| --- | --- | --- |
| ✨[Feat] | 페이지, 사용자 기능, 기능용 API 추가 | 제목에 기능 설명 |
| ⚙️[Core] | 라우팅 기반, API 클라이언트, 인증 기반, 공통 인프라 | 제목에 기반 작업 설명 |
| 🐛[Fix] | UI·API·인증·접근성 등의 잘못된 동작 수정 | 제목에 현상, 본문에 해결 방법 |
| ♻️[Refactor] | 동작 변경 없는 컴포넌트·훅·서버 코드 구조 개선 | 제목에 구조 개선 내용 |
| 🗺️[Design] | 레이아웃, 반응형 구성, 시각 계층, UX 흐름 개선 | 제목에 개선 대상 상태, 본문에 조정 방법 |
| 🩹[Patch] | 문구 오타, 작은 간격 등 사소한 손질 | 제목에 개선 대상 상태, 본문에 변경 방법 |
| 🗃️[Update] | DB 스키마, 마이그레이션, 시드 데이터 변경 | 제목에 데이터 변경 내용 |
| 🎨[Asset] | 이미지, 아이콘, 폰트 등 정적 리소스 변경 | 제목에 리소스 변경 내용 |
| 📝[Docs] | README, API 문서, 운영 안내, 주석 | 제목에 문서 변경 내용 |
| 🧹[Chore] | 의존성, 린트, 빌드 설정, CI/CD, 배포 설정 | 제목에 관리 작업 내용 |
| 🔀[Merge] | 브랜치 병합 | 제목에 병합 대상과 목적 |
| 🔥[Del] | 페이지, 기능, API 제거 | 제목에 제거 대상 |
| 🎉[Init] | 웹 프로젝트 초기 구성 | 제목에 초기 구성 내용 |
| 💚[Build] | 버전별 빌드 산출물 생성 | 제목에 버전 표기 |

### 라벨 선택 기준

- 사용자 기능이나 기능용 API는 `Feat`, 여러 기능이 사용하는 기반 구조는 `Core`다.
- 로그인 화면·로그인 기능 추가는 `Feat`, 공통 세션 관리 기반은 `Core`다.
- CSS 변경도 깨진 레이아웃이나 사용 불가 상태를 고치면 `Fix`다.
- 정상 동작하는 화면의 레이아웃·사용 흐름을 개선하면 `Design`, 작은 간격·오타 손질은 `Patch`다.
- `Refactor`는 동작 변경이 없어야 한다. 성능 개선으로 실행 방식이나 로딩 동작이 바뀌면 목적에 따라 `Core` 또는 `Fix` 등을 쓴다.
- 이미지 파일 자체 교체는 `Asset`, 이를 포함한 새 페이지 구현은 `Feat`다.
- DB 변경은 `Update`, 라이브러리 버전 업데이트는 `Chore`다.
- 빌드·배포 설정 변경은 `Chore`, 실제 빌드 산출물 생성은 `Build`다. 산출물은 저장소 정책상 추적할 때만 커밋한다.
- 테스트는 관련 기능·수정 커밋에 포함한다. 테스트만 추가·정비하는 별도 커밋은 `Chore`를 쓴다.

### 예시

```text
✨[Feat] 상품 검색과 필터 추가

* 검색어와 필터를 URL 쿼리에 반영
* 검색 결과 로딩 및 빈 상태 표시
```

```text
🐛[Fix] 로그인 만료 후 빈 화면 표시

* 인증 오류 발생 시 로그인 화면으로 이동
* 재로그인 후 돌아갈 경로 보존
```

```text
🗺️[Design] 모바일에서 주요 버튼의 낮은 가시성

* 주요 버튼을 첫 화면에 배치하고 보조 동작과 시각적으로 구분
```

```text
🩹[Patch] 회원가입 안내 문구 오타

* 이메일 인증 안내의 잘못된 표기를 교정
```

```text
🔀[Merge] 검색 기능을 개발 브랜치에 병합

* feature/search를 develop에 병합
```

자동 생성된 머지 메시지도 한국어 제목과 정해진 형식으로 정리한다.

### 커밋 전 체크리스트

- [ ] 이모지와 라벨이 표의 짝과 일치하는가?
- [ ] 한국어 제목이 50자 미만이며 끝에 마침표가 없는가?
- [ ] 한 가지 목적의 변경만 포함하고 제목이 구체적인가?
- [ ] `Fix`, `Design`, `Patch`는 제목에 현상, 본문에 해결 방법을 썼는가?
- [ ] 여러 변경 항목과 임시 처리·후속 작업을 본문에 남겼는가?
- [ ] 커밋 대상 diff에서 관련 없는 기존 변경, 비밀 정보, 불필요한 산출물을 제외했는가?
- [ ] 변경에 필요한 검증 결과를 확인했는가?

## 웹 구현 기준

- 먼저 프로젝트의 README, 패키지 스크립트, 잠금 파일, 기존 컴포넌트와 스타일을 확인한다. 기존 프레임워크·패키지 매니저·디자인 체계를 우선 사용한다.
- 새 프로젝트에서 기술 선택이 명시되지 않았다면 요구사항에 맞는 최소 구성을 선택하고 선택 이유를 설명한다.
- 사용자에게 보이는 문구는 요청 언어를 따르고, 기존 디자인 토큰과 공통 컴포넌트를 재사용한다.
- 모바일과 데스크톱에서 콘텐츠·내비게이션·주요 동작을 사용할 수 있게 구현한다. 고정 너비로 인한 가로 넘침을 확인한다.
- 의미에 맞는 HTML을 사용하고 키보드 조작, 포커스 표시, 폼 레이블, 이미지 대체 텍스트를 제공한다.
- 데이터 요청과 폼에는 필요한 로딩·빈 결과·오류·성공 상태를 구현한다. 중복 제출과 입력 손실을 방지한다.
- API 입력 검증과 권한 확인은 서버에서 수행한다. 비밀 키·토큰은 클라이언트 코드나 저장소에 넣지 않는다. 환경변수 예시는 실제 비밀 값 없이 제공한다.
- 서버 데이터와 클라이언트 상태의 역할을 구분하고, 불필요한 의존성·중복 상태·과도한 추상화를 추가하지 않는다.
- 이미지 크기와 로딩 방식, 불필요한 요청·렌더링을 확인한다. 최적화 결과는 측정한 범위에서만 주장한다.

## 검증과 보고

- 기존 스크립트에 따라 변경에 필요한 린트, 타입 검사, 테스트, 프로덕션 빌드를 실행한다.
- 화면을 바꾸면 가능한 브라우저 도구로 모바일·데스크톱 주요 화면, 핵심 사용자 흐름, 콘솔 오류를 확인한다.
- 버그 수정이나 중요한 로직 변경에는 원래 오류 또는 회귀를 검출할 수 있는 테스트를 적절히 추가한다.
- 도구·환경·인증 부족으로 실행하지 못한 검증은 완료로 보고하지 않고 이유와 남은 항목을 알린다.
- 완료 시 변경 내용, 검증 결과, 남은 제한을 간결하게 보고한다.

## 파일과 작업 범위

- 소스와 문서는 기존 파일 형식을 존중하고 새 텍스트 파일은 UTF-8 BOM 없이 저장한다.
- 작업 전 저장소 상태를 확인하고 사용자의 기존 변경을 덮어쓰거나 되돌리지 않는다.
